# Make It Lean：技能构建与复用说明

版本：1.1.2。日期：2026-11-01。技能标识：`make-it-lean`。

这份说明供安装、分享和维护技能的人阅读。分享 [GitHub 仓库](https://github.com/indulge-gif/make-it-lean) 即可让对方在自己的项目中安装使用；agent 的执行入口是 SKILL.md。

## 1. 它解决什么问题

Make It Lean 将“承接已有成果、沿既定目标与路线推进、自主判断文件价值、交付实际产出”作为一套项目工作方式，适用于软件开发、论文复现、实验、文档及其他产出型项目。

Lean 指减少无效流程和存量负担。项目即使包含大量素材、模型或历史产物，也可以采用这套方法；资源保留依据其用途和项目目标判断。

| 场景 | 技能要形成的结果 |
|---|---|
| 新项目开始 | 建立少量可持续的开发约定，确定文档、产物、验证与 Git 交付方式 |
| 现有项目精简 | 承接有效成果与既定路线，收敛入口和文档，按价值处理历史产物，完成依赖更新与必要验证 |
| 后续持续开发 | 把实现、验证、清理、状态更新和已授权的同步一起完成，减少维护债务 |

## 3. 核心行为的具体含义

### 3.1 最高原则：承接已有成果，沿既定目标与路线推进

以用户已确认的目标、路线、有效成果及验收依据为基线。规则建立与整理服务于原项目，保持成果的价值、可用性、可追溯性和后续工作的连续性。

软件项目承接已有功能、接口和数据契约；论文复现与实验承接来源、协议、关键参数、对照和结果；文档及其他产出项目承接结构、引用、交付要求与有效中间成果。

任务范围内可以修复问题、比较方案和适度重构。替代、迁移或修正完成后，核对相关依赖和成果再处理旧项。发现错误时根据证据修正并说明变化；已有成果的有效性与文件保留价值分别判断。目标或关键路线的实质变化按照项目决策方式处理。

这条原则位于 SKILL.md 最前面，影响后面的清理、验证与 Git 决定。

### 3.2 自主推进，把问题补足后交付

能够通过阅读、查阅、复现、对照、修复和复测处理的问题，由模型形成具体下一步并执行。尝试根据新假设或新证据推进，一种路径反复失败时调整诊断方式。

在用户目标、授权与资源范围内，模型自行作出实施判断。真实缺少关键外部条件或需要用户决定关键取舍时，反馈已完成成果、阻断证据、尝试结果、建议与恢复办法，继续处理独立部分。

计划与执行提示词集中描述目标、技术路线、操作、交付和验收，长期约定通过项目说明继承。用户要求先规划或等待审核时，交付对应阶段的成果。

### 3.3 主动判断文件价值

文件保留由用途、消费者、独立价值、可重建性及项目保留约定支持。模型在整理授权范围内自主决定保留、合并、提炼、替换或删除，更新引用并验证。

典型处理：

- 已被替代的入口和重复模块：收敛消费者、验证正式实现后清理。
- 临时脚本、截图、缓存和重复导出：用途结束后及时删除。
- 历史报告和规划：提炼当时的方法、实际效果及决定，合并冗余内容。
- 仍用于复现和恢复的资料：保存最小有效集合，写清具体用途。
- 唯一资料、人工标注、必要资源和其他人的工作：依据真实价值及既有约定处理。

文件年代、名称和“可能还有用”作为调查线索。归档应服务实际恢复或追溯需求，避免将所有旧文件重新打包后永久保留。

本技能中的文件“删除”“移除”“清理”默认采用系统回收站，临时产物也适用。使用明确支持回收站的方式；不可用或失败时保留失败项并说明，不自动改为永久删除，不自动清空回收站。用户明确授权永久删除时才执行该方式。回收站用于降低误删损失，不替代必要资料的长期保留。遇到审核拒绝，依据理由采用实质更安全的方案；换工具执行同一被拒操作不属于降低风险。

### 3.4 交付说明已确认的成果

交付正文说明做成什么、实际验证支持什么、产物在哪里，必要时简述适用范围和下一步。可补足的检查在过程中完成，减少产物里反复出现“未验证”“未证实”等过程标签。

实际观察到的失败也是结果，按输入、现象与证据说明。事实、推断和计划分别表达；真实阻断单独交付诊断与恢复建议。成果表述与实际执行一致。

### 3.5 让操作与实际需要相称

“先核验、冻结、备份，再跑全套测试，最后通过全部门禁并归档”包含了多种不同问题的处理手段。将它们串成常规工作流，会让普通任务承担生产发布、灾难恢复和专项审查的成本。技能约束的是选用这些手段的理由和范围，技术词语本身可以正常使用。

这类行为有四个需要纠正的倾向：

- **流程代替目标。** 从术语推导步骤，做了大量操作却没有回答本次任务的问题。每项额外操作应解决具体缺口，结果会影响实施或交付决定。
- **反复消除同一不确定性。** 已有结果、当前代码和明确授权被不断重新检查；检查还可能引出新的备份、清单和复核。复用适用结果，只针对相关变化、新故障或新证据补充。
- **把局部任务扩成全面保证。** 为一处改动安排所有测试类型，或追求“没有任何副作用”的结论。验证覆盖受影响行为，交付如实描述这个范围；确有共享影响、生产或专项要求时再扩大。
- **用过程留痕证明工作量。** 交付堆叠检查名、日志、哈希和免责声明，读者仍看不出结果。正式记录保留产物、关键结果、必要来源和实际限制，临时材料用途结束即清理。

模型自行完成这种取舍，普通任务不另写一份风险矩阵来证明自己有资格省略流程。沿用已有项目要求与用户明确要求；规则整理时可以有依据地精简冗余规则。

工程手段的具体适用情形集中在 [项目建立与存量整理](../references/project-adoption.md#按具体问题选择工程手段)。例如，唯一原始数据搬迁可能需要字节比对和恢复准备；修正文档链接通常查看目标与差异即可。对比实验需要固定影响比较的输入和条件，单个函数修复则可直接复用相关测试。

**执行的完成条件：** 目标已经达成，相关检查足以支持交付结论，且没有影响该结论的具体未解决问题。此时完成整理和已授权同步，交付结果；后续检查由新问题或变化触发。

**表达的选择：** 已能补足的问题在过程中解决；与交付无关的不确定性不展开，影响使用或决策的限制简要说明范围和后续办法。例如：

| 情形 | 直接表达 |
|---|---|
| 修复已经完成，相关测试通过 | “已修复导出错误，相关3项测试通过，文件位于……” |
| 只在一种素材上得到结果 | “在这段素材上，漏检由12处降至5处。” 保持结论范围，不扩展为跨素材有效 |
| 生产环境需要用户提供权限 | “本地修改和测试已完成；部署需要目标环境权限，取得后执行……” |

减少防御性表达的同时保持事实准确。负结果、重要限制和实际阻断照常报告，已做的检查按真实范围命名。

## 4. 通用约定与项目选择

| 通用要求 | 项目如何适配 |
|---|---|
| 固定主文档目录 | 沿用已有目录；新项目默认 docs/，README、AGENTS 等约定入口保留原位 |
| 减少文档增殖 | 优先原位更新；独立且长期的职责才新建文件，真实内容出现时再建子目录 |
| 生成产物集中管理 | 复用框架与项目现有位置，额外试验使用约定的输出根目录 |
| 验证与实际效果 | 根据项目类型和受影响成果选择验证；本次目标与已有成果连续性一起检查，结论以实际结果支持 |
| Git 连续交付 | 原项目未纳入 Git 时直接交付文件，用户明确要求后才启用 Git；已有仓库沿用合适分支与已有授权同步 |
| 协作按需选择 | 一个对话可以完成全流程，长任务或明确需要时再分角色、窗口或 agent |
| 状态主动维护 | 新的持久信息、可恢复成果、决定变化、交接和结束时更新；小任务合并记录 |
| 操作与需要相称 | 追加操作解决具体问题，复用适用结果，充分后交付；专项流程按实际影响选择 |
| 模型与工具 | 沿用用户偏好及项目资源；具体型号、付费计划和固定窗口数量由项目决定 |

技能不绑定某个项目的目录、阶段号、素材类型、仓库地址或模型。用户最新决定及项目实际约定控制具体实施，技能负责补充可持续的工作方式。

使用时选择与任务有关的部分，无需逐条执行或证明遵守。文档作为接续索引，结合当前源码和实际产物判断；过时内容在相关范围核对后原位修正。整理覆盖本次产生或替代的内容，大范围整理以授权为准，正常模块和有效资料依用途保留。探索讨论不自动变更主线或生成文件，形成决定后再更新相关记录。

## 5. 安装与转发

### 个人使用：适用于多个项目

按当前 Codex 官方本地技能约定，将完整文件夹放到用户的 `~/.agents/skills/make-it-lean/`。

Windows PowerShell：

```powershell
$leanSkillsRoot = Join-Path $env:USERPROFILE '.agents\skills'
New-Item -ItemType Directory -Path $leanSkillsRoot -Force | Out-Null
git clone https://github.com/indulge-gif/make-it-lean.git (Join-Path $leanSkillsRoot 'make-it-lean')
```

macOS / Linux：

```bash
mkdir -p ~/.agents/skills
git clone https://github.com/indulge-gif/make-it-lean.git ~/.agents/skills/make-it-lean
```

确认最终目录是 `skills/make-it-lean/SKILL.md`，保持同名技能只有一个权威安装来源。已有同名版本时，比较差异后更新原目录；通过 Git 克隆安装且无本地改动时，可在技能目录执行 `git pull --ff-only` 更新。未通过 Git 安装的旧版本按文件更新即可。

Codex 会发现技能变更；在新对话中输入 `$make-it-lean` 调用。若界面没有刷新，重启客户端。

### 项目共享

希望团队共同使用时，将完整目录放到项目的 `.agents/skills/make-it-lean/` 并按该仓库规则提交。技能引用使用相对路径，可以随仓库迁移。

使用其他 agent 时，放到该工具支持的技能目录，或让它读取 SKILL.md 执行；`agents/openai.yaml` 是 Codex 界面配置。

以 GitHub 仓库作为分享与版本维护入口，本地保留实际使用的技能目录，无需额外维护迁移压缩包。团队以后需要多个技能或连接器一起分发时，可以另行包装成插件。

## 6. 直接复制的使用方法

### 新项目建立约定

```text
使用 $make-it-lean，围绕本项目目标建立精简的开发约定。沿用已有结构，明确主文档目录、临时产物、必要验证、保留要求与 Git 交付方式，把长期规则合入现有项目说明。
```

### 精简已有项目

```text
使用 $make-it-lean，按照当前项目既定目标与路线整理现有仓库。先确认有效成果、入口、依赖与验收依据，主动判断历史文件与临时产物的价值，完成必要归并与重构，核对成果连续性并交付实际结果。
```

### 持续开发

```text
使用 $make-it-lean，按项目现有目标和路线完成本次任务，自主补足能够处理的问题，承接已有有效成果，完成必要验证、产物清理、状态更新和已授权的 Git 同步，交付实际结果与入口。
```

需要长期接续时，让模型将少量持续适用的规则写入项目 AGENTS 或等效说明，之后可以只交代具体任务。项目文件承载项目约定，技能包承载通用方法。

## 7. 怎样重建与维护这个技能

本技能以四个执行文件和一份人用说明构成，仓库 README 提供公开首页和安装入口。从 GitHub 安装即可；只有本说明时，可以将以下指令交给具备文件操作能力的 agent：

```text
依据这份《Make It Lean：技能构建与复用说明》创建 make-it-lean 技能，采用其中五文件结构。SKILL.md 前置“承接已有成果，沿既定目标与路线推进”，适配软件、复现、实验、文档等项目；写入自主推进、文件价值判断、已确认成果交付及文档/Git 规则。初始化和存量整理细节放 project-adoption.md，可选接续放 collaboration.md。生成一致的 openai.yaml 与简短默认提示词，校验元数据、相对引用和实际样例，整理为可安装目录；分享和更新使用仓库链接。
```

构建时可使用 skill-creator 的初始化、界面元数据生成与校验工具；这些工具是构建辅助，不是技能运行依赖。

维护要点：

1. 保持目录名、SKILL.md 的 name 和调用名 `make-it-lean` 一致。
2. description 描述建立约定、现有仓库精简及按本流程持续交付这些场景，保持简短。
3. 默认保留正常自动发现；显式 `$make-it-lean` 适合首次采用或明确要求应用本流程。
4. 通用规则在 SKILL.md 修改；仅部分任务需要的内容放 references，并说明读取条件。
5. 更新行为后核对本说明和相对引用；实际项目需求放进该项目，避免将特定案例累积成全局限制。
6. 出现稳定、重复且适合确定性自动化的操作时，再引入脚本，并验证其实际副作用。

## 8. 验证方法

结构校验检查 name、description、元数据、相对引用、代码围栏和未完成的初始化占位内容。界面说明与默认提示词应和技能用途一致。

样例验证检查实际文件、功能和 Git 结果：

- 已有 documentation/ 的项目继续使用原文档目录，现有目标和路线保持。
- 根据项目检查已有行为或成果与当前改动；能够修复的问题完成定位和复测。
- 实验交付保持既有输入、协议和基线结果的可追溯性，新增比较表按同条件计算。
- 过时入口和临时产物完成用途核对后清理，必要资料和他人改动保持。
- 既有分支和既有同步授权得到沿用，暂存范围与本次任务一致。
- 交付说明给出实际结果和入口，过程性证据缺口在实施中处理。

验证使用隔离示例目录和本地测试远端，结束后清理样例。保持失败诊断与实际适用范围清楚，规则修改依据可观察结果进行。

### 初版样例验证记录（2026-10-29）

| 验证 | 本次实际结果 |
|---|---|
| 技能结构 | SKILL格式校验通过，界面元数据与用途一致，6处包内相对引用可解析 |
| 软件样例 | 复现3项计价错误，修复后5项行为测试通过，包含原有2项收据格式测试；清理后入口冒烟通过 |
| 成果与资料承接 | 软件样例的原数据指纹一致，原收据实现保持；实验样例的输入、协议、评估脚本及既有基线结果共4份文件指纹一致 |
| 实验交付样例 | 固定4个合成样本与MSE口径，生成两行比较表；baseline为4.5，candidate为1.5，沿用原CSV评估路线 |
| 文档与清理 | 两类样例均沿用 documentation/；废弃启动入口、一次性探针和重复导出按用途处理，原有效结果保留 |
| Git交付 | 软件样例沿既有 trunk 分支完成范围内提交，本地测试远端提交一致；分支数保持1，他人未提交改动保留且未进入本次提交 |
| 无Git项目 | 实验样例保持其原有无Git布局，直接交付结果文件与说明 |

这些记录对应初版隔离样例的实际操作、数值与文件状态；样例数据用于核对工作流，不代表每次规则修改都重跑这些场景。
