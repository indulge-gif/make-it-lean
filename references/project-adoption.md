# 项目建立与存量整理

在用户要求建立开发约定、精简已有项目或调整工作方式时读取。以现有项目、用户目标和实际消费者为依据，按任务需要选择下面的做法。

## 选择入口

| 阶段 | 具体结果 |
|---|---|
| 新项目建立 | 明确主文档目录、生成产物位置、必要验证、状态入口及 Git 交付方式，把少量长期约定合入 AGENTS 或项目现有说明 |
| 已有项目精简 | 梳理用途、引用与已有成果，确定正式入口与权威文件，处理重复内容和失效实现，更新依赖并验证实际流程 |
| 持续开发 | 沿用既有布局，范围内实施与重构，结案时整理产物、更新结果、按授权同步 |

按当前任务读取必要的项目约定、目标、成果与实施入口。明确的接手或全面整理才梳理整体资源、目录和 Git 状态；普通修改直接利用相关源码、资料与配置，信息足够后开始实施。

整理以已有有效成果为基线，先识别受影响的依赖、引用和对应验收；替代、迁移或修正完成并验证后处理旧项。软件项目关注功能与接口，实验或复现关注协议、数据、参数和结果，文档项目关注结构、引用及交付要求。目标收益与成果连续性一起验收。

## 建立最少且持久的约定

优先更新现有项目说明；采用 AGENTS 时保持简短，让其他开发者也能看懂。只记录会持续影响决策的内容：

- 当前目标与相关实现入口。
- 唯一主文档目录、生成产物和临时内容的位置。
- 本项目实际的运行、验证和必要资源准备方式。
- 文件保留要求及提交、推送、分支约定。
- 需要长期接续时的当前任务与状态入口。

项目专用信息留在项目中；通用方法由技能维护。一次性小任务可直接更新已有说明或任务记录，较长项目才按需要分离计划和状态。

优先从现有会话和项目说明识别授权。只有真正影响当前推进的目标或资源取舍无法推断时，集中提出具体问题，并继续处理独立部分。

## 固定文档目录，减少文件增殖

1. 需要文档时使用项目已有主目录，缺少时默认采用 `docs/`；任务本身不要求创建成套目录和文档。README、AGENTS、许可证及生态约定入口保留原位。
2. 先更新现有内容；按职责组织，避免每项小任务新建计划、交接、提示词和总结文件。
3. 多份材料承担相同职责时，选一份权威内容，合并有用信息、更新入口，再清理冗余副本。
4. 计划和状态原位维护；阶段结果汇总问题、方法、可比结果和采用决定。历史快照只为明确的恢复或追溯需求保存。
5. 子目录承载真实内容与独立职责，有内容再创建。用户需要人用指南时，提供清楚入口和少量可复制指令。

在已经使用 `documentation/`、`doc/` 或站点文档系统的项目，保持其约定；统一的是入口与职责，不是批量改名。

## 自主作出保留、归并与删除决定

结合调用、导入、配置、启动入口、链接、构建规则、内容和版本历史判断。动态消费者、合规保留和复现用途与直接引用同样有效。

| 发现 | 处理 |
|---|---|
| 正在运行的实现、必要资产、固定测试 | 保留或按本任务重构，验证其消费者 |
| 多个等价入口或重复模块 | 选定正式入口、收敛实现与调用，验证后清理替代项 |
| 过往报告和旧规划反复描述相同结论 | 提炼阶段差异、实际效果和决定，合并后处理冗余原件 |
| 一次性调试脚本、截图、缓存、重复导出 | 用途结束后清理；需要的结论并入正式记录 |
| 可再生成且没有持续用途的备份或快照 | 清理，说明对应类别与影响即可 |
| 仍用于复现或定位的必要材料 | 保留最小有效集合，写清用途和恢复方式；用途结束时再处理 |
| 唯一资料、原始数据、人工标注 | 依据实际价值及项目保留约定决定，沿用用户明确的整理授权 |
| 其他参与者的未完成工作 | 核对归属与当前用途，在协作约定范围内处理 |

文件旧、名称含 temp、没有搜索到静态引用，都只是线索。“可能还有用”也不是完整保留理由。通过足够的核对形成判断，能够判断的整理事项由模型自行完成。

归档要能说明为什么以后需要恢复；对重复备份和可重建产物，合并压缩不能替代价值判断。确实缺少关键依据时，把缺少什么、已有证据和推荐方案集中反馈。

## 执行整理并完成验证

按用途形成合理批次，每批完成依赖更新和必要验证。路径迁移检查身份、链接及消费者；软件流程重构检查固定回归和实际入口；实验调整核对数据、协议、参数、基线与结果的对应关系；文档调整检查结构、引用和交付要求。根据改动范围承接已有成果，沿已确认的路线交付改进。

清理范围使用已确认的路径和实际归属。必要的短期恢复安排以具体风险为依据，验证完成后处理其生命周期；避免形成新的永久备份堆积。

保留一份足够解释结果的记录：收敛了哪些职责、删除了哪些类别、实际验证与后续入口。较大规模操作需要的清单用于执行与核对，结案后提炼正式记录。

## 按具体问题选择工程手段

下表用于有需要时作取舍，不是逐项执行清单，也不是禁用词表。只有会影响当前实现或交付决定的问题才值得追加操作。

| 手段 | 有实际用途的情形 | 常规任务的直接做法 |
|---|---|---|
| 核验、检索、探针、检查、审计、评估 | 当前事实缺口影响实现，故障需要定位，或用户要求专项审查 | 先读相关实现与已有结果，缺什么补什么；同一事实一次获取后复用 |
| 目标、约束、边界、验收、唯一基线、冻结 | 目标确有歧义，比较条件需一致，多方依赖需要稳定版本 | 沿用已确认任务与当前版本；明确的小改动直接执行，比较实验只固定影响可比性的条件 |
| 快照、备份、恢复演练、回滚 | 唯一资料或不可逆数据将改变，生产操作需恢复准备 | 普通可恢复文件修改使用现有版本记录；恢复安排覆盖具体损失及操作，不为每次修改另存整套副本 |
| 哈希、SHA256、指纹、一致性 | 需判断传输或迁移是否改变字节、核对分发文件，或识别实验输入版本 | 文本改动看差异，结构化结果看内容；确需逐字节比对时采用合适方式，哈希只回答身份与字节一致性问题 |
| 测试夹具、静态/单元/集成/回归/冒烟测试 | 已定位的缺陷、受影响接口与消费者需要覆盖 | 选能暴露该问题的已有测试或实际输入；新增测试服务持续回归价值，不按测试名称凑齐全套 |
| 安全检查、性能验证、故障注入 | 改动触及权限、攻击面、性能目标或容错机制，或用户明确要求 | 围绕受影响机制验证；文案、路径说明等普通修改不附带无关专项流程 |
| dry-run、灰度、放量、门禁 | 批量外部操作或生产部署确需预演、分阶段发布；仓库已有必需检查 | 普通本地任务直接实施并检查结果，沿用实际 CI 要求；不新增形式化关卡 |
| 验收矩阵、证据链、统一归档 | 多项交付或研究追溯确需结构化对应关系 | 复用现有记录，保留关键结果及必要来源；过程日志、临时清单和重复导出用途结束即清理 |

操作是否必要取决于它解决的问题，同一种手段可在一个项目中必要、在另一个项目中多余。检查结果已覆盖当前问题且相关改动未变化时，继续实施或交付；追加检查由新问题触发。已有项目规定的必需流程仍按其要求完成，冗余约定在规则整理任务中原位修订。

## 生成目录与 Git 忽略规则

复用项目或框架已有的 build、dist、target、coverage、测试临时目录等布局。额外的试验与报告进入约定的输出根目录，临时内容按任务收纳。

按用途维护 `.gitignore`：

- 本机环境、凭据、缓存、日志、临时试验及重复生成的输出通常留在本地。
- 正式源码、必要资产、合成测试夹具、关键实验配置、精简结果记录与正式文档按项目需要跟踪。
- JSON、CSV、图片、压缩包等格式既可能是源码资产，也可能是临时产物，结合目录和用途选择规则。
- 模型、数据和大型二进制的保存方式沿用项目的资源与交付设计。

同时检查已被跟踪的生成文件。忽略规则影响后续发现，已跟踪内容应按本次授权和保留决定处理索引；保留本地数据与移出版本控制是不同操作。

## Git 策略与规则更新

先确认项目是否已纳入 Git。未纳入时直接交付文件、结果与必要说明，保持原有工作方式；只有用户明确要求使用 Git 时才初始化仓库、提交或安排远端同步。

沿用合适的当前分支、实际默认分支及仓库保护规则。常规维护可以直接在允许的默认分支交付；独立并行、探索保存和互审需求才引入短期分支。

已有常规提交与推送授权时，将同步纳入每项可交付步骤及交接。尚未明确的仓库策略先从现有任务与说明判断，需要用户选择时只处理真正影响交付的缺口，确定后写入现有约定。

整理结束前检查主入口、引用、验证结果、暂存范围和同步状态。长期规则在实际条件变化时原位调整，避免叠加第二套互相竞争的说明。
